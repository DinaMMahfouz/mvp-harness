| 4 | AI Assurance Engineer | Backend/Data Engineer | `SYSTEM_PROMPT_LEAKAGE` deterministic checks are only as good as the strings they match against — free-text substring/regex scanning of `model_response` alone is unreliable (system prompts get paraphrased, not always echoed verbatim by an attacker's exact framing) and would either miss real leaks or need constant hand-tuning. | Chose deterministic protected-marker matching over pure LLM judgment for `SYSTEM_PROMPT_LEAKAGE`: `run_deterministic_check` in `backend/app/evaluators/deterministic.py` takes an optional 5th parameter `protected_markers: list[str]`. **The Backend Engineer must populate this from the application's actual system-prompt/config text (e.g. a few distinctive verbatim sentences or internal codenames) and pass it through `pipeline.evaluate(..., protected_markers=...)` for every SYSTEM_PROMPT_LEAKAGE test case.** Without markers, those cases silently fall through to the Claude evaluator every time (still correct, just not free/instant). This keeps the highest-value leakage checks reproducible and zero-cost while leaving paraphrased/partial leaks to Claude's semantic judgment. |

| 7 | QA/Devil's Advocate | Backend/Data Engineer, AI Assurance Engineer | **Primary documented defect** (full narrative in `docs/qa-review.md`): `scoring_service.score_run()`/`decide_release()` — the only DB-facing code path that actually computes `assurance_score`/`release_decisions.decision` in production — scoped their `Finding` query to `last_seen_run_id == run.id`. Since `finding_service` only bumps `last_seen_run_id` on a re-confirmed FAIL/REVIEW (never on PASS, and never auto-resolves), a still-OPEN CRITICAL finding from an earlier run silently stopped counting toward scoring/decision the moment a *later* baseline run (a normal, user-triggerable `POST /runs` re-run, not hypothetical) didn't happen to re-fail that same case — flipping `NOT_READY` to `READY_WITH_CONDITIONS`/`READY` with nothing actually fixed. Root cause: run-scoping that `docs/release-readiness.md`'s plain-language rules never asked for, plus zero prior test coverage on the DB-facing wrappers (only the pure `compute_*` functions were unit-tested). | Removed the `last_seen_run_id == run.id` filter from both queries in `backend/app/services/scoring_service.py` — findings are now scoped by `application_id` + `status` only, matching the spec. Added `backend/tests/test_scoring_db_integration.py` (new DB-integration coverage) and reran the full suite: `28 passed`. Also found and fixed a related gap while re-deriving the decision rules by hand: an `ACCEPT_RISK` **CRITICAL** finding fell through both the NOT_READY and READY_WITH_CONDITIONS branches entirely (only `ACCEPT_RISK` **HIGH** was checked), letting an explicitly-accepted CRITICAL risk reach an unconditional `READY` with zero trace of it, contradicting the docs' note that "ACCEPT_RISK is still visible in the rationale trace." Added the missing check + a unit test (`test_ready_with_conditions_on_accept_risk_critical_finding`). |
